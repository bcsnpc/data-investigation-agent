# Offline retry inputs from a published parent

`python scripts/prepare_runner_retry_inputs.py --help` builds a new input ZIP from an original input ZIP and the eight exact, restored `prepared` CAS dependencies. The source ZIP and dependency manifest are hash-pinned. The real readonly ModelStore read must equal the retained model record, including its events and context history. Its retained discovery source must still exist. The derived ZIP copies the prepared catalog and inventory byte for byte; only its request key and owner/provenance record otherwise change. Originals are never opened for writing. The builder makes no network or model calls.

The CLI requires a local restored dependency folder. An operator may restore it with existing `Files.restore` through `restore_dependencies`; the operator owns that separately admitted platform access. This command never falls back to a stale catalog or rewrites historical runs.

The first Part C attempt published model revision 84 but exhausted its verification deadline before any diagnostic or physical request. The next input must therefore use that exact published parent, not revision 83 from the first ZIP. The new approval and context are still constructed inside the current worker image through the ordinary publication path.

## Deadline finding and correction

The handler currently computes the native verification deadline before the capture constructor audits and snapshots the full SQLite databases and before pre-read dependencies are retained. Those controls consumed the 900-second native-read window on the first attempt, which recorded `VERIFICATION_DEADLINE` with zero physical/diagnostic/model requests. Retention after that failure remained subject to the 1,800-second Azure job limit.

Keep the overall 1,800-second envelope anchored at runner entry. Start the native verification window only after pre-read capture and dependencies are durable; allow the configured native window (at most 1,800 seconds) and clamp it to the remaining envelope after explicit demo and finalization reserves. If insufficient time remains for a bounded query and settlement, record timing unavailability and admit no query. Record the start with a tape clock event and derive its deadline deterministically. Do not alter a sealed bootstrap deadline or reinterpret old tapes. Settlement of an existing reservation remains possible after the read-admission deadline. This separates a diagnostic window from controls without increasing any cap. The separate native-window correction implements this recorded clock and reserves 120 seconds for finalization plus 300 seconds when a combined demo is configured. It refuses a native window with less than 60 seconds left and refuses demo admission when its reserve no longer fits. The Azure job remains the hard 1,800-second process ceiling; ordinary form intake and adaptive session deadlines remain their existing contracts. The demo admission reserve does not claim to shorten those independent internal deadlines.


DECIDED WITHOUT REVIEW ? 2026-10-21: Removed the implementation's self-imposed 900-second maximum for the native window. Rejected retaining that maximum because it was inherited from an old configuration, not an owner cap, and could make the approved 40-probe verification impossible after controls. A configured 1,200-second native window is valid; its effective deadline remains the earlier of its start plus that duration and the original absolute 1,800-second job deadline minus explicit reserves. The default remains 900 seconds. This does not increase the overall job, monthly budget, probe cap, or any other allowance.


Bounded-memory snapshot correction ? 2026-10-21: The verifier snapshot now opens the source readonly, begins a read transaction, audits schema and every row in that frozen view, and backs up the same connection only after all checks pass. It no longer copies the entire database to an in-memory SQLite database. Raw and normalized BLOB checks, before-write refusal and exact written-file attestation remain. WAL writers may commit concurrently, but their later changes cannot enter the already-audited read snapshot. Memory remains proportional to the largest row/cell and bounded audit batch rather than total database size; this does not claim arbitrary single cells have a fixed memory bound. The overall job and resource allocation are unchanged.


Image CI includes the streaming-snapshot, batching, run-audit-reuse, native-window, current-context, unified-runner, graph-schedule and exact-capture suites alongside the original ten modules, using the same eight shards. The memory regression creates a 96MiB database (48 two-MiB BLOBs); source plus destination fit the 256MiB temporary filesystem. Linux uses peak RSS and Windows uses the standard process memory counters; both require peak growth below 96MiB. No additional resource or paid runner is created.
