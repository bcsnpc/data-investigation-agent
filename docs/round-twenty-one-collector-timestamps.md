# Collector timestamp failure and status freshness

Offline diagnosis, 2026-10-22. Scheduled and manual collection retained successful Fabric job-instance responses, then failed with `GRAPH_TIMESTAMP_TIMEZONE_REQUIRED` before writing facts. The retained source results are pinned at `.local/round-twenty-one/collector-failed-source-results.json`: physical result 9 SHA-256 `4e0b5e5caac3186db8222c1d84c69796c4c2db1d27da2134b66b055fbd801a8f`; result 10 `a11aeef015c3ae2dd0edb3ec6886eaa03df35b3bf453e2fce6b54598cfc9dc5d`; failure 11 `61a1edf52e1a9f228da9faab858398796a77678b0746f2f3a886bd74a249523b`.

For example the first body declares `startTimeUtc: 2026-10-09T21:51:03.1830083` and `endTimeUtc: 2026-10-09T21:55:02.3066667`, status `Completed`. The second declares endTimeUtc `2026-10-09T21:59:35.88`. These explicitly UTC-labelled API fields omit an ISO offset. The adapter formerly copied them into generic start/end without preserving that timezone declaration. Derived duration parsing then correctly refused the resulting timezone-less generic timestamp.

The adapter now adds UTC only for the producer's `startTimeUtc`/`endTimeUtc` fields, then passes the value through the existing strict canonical timestamp function. Aware offsets remain normalised by that function. Generic `startTime`/`endTime` without an offset still refuse; there is no blanket naive-time assumption. Declared SQL audit aliases inherit UTC only from the exact configured `start_time_utc`/`end_time_utc` columns. Raw source receipts are unchanged, including the original seven fractional digits; canonical fact timestamps use the contract's existing microsecond precision.

Status freshness already measures age since `collected_at`, not event completion. The current collector sets observation/collection time to the listing read; event start/end stay separate inside the run value. Consequently an October 9 last run can answer an explicit last-run status question from a fresh October 22 listing. That does not establish recent data, a load watermark, or a common snapshot. A new regression verifies current status from that recent listing, the unchanged old event end, no TABLE_LOAD/TABLE_PROFILE inference, and staleness after the configured collection-age bound. No eligibility, coverage, read-only, incident-causality or attestation guard was relaxed. No contract extension is needed for this fix.

Offline validation: runtime-facts and facts-ledger suites ran 39 tests: 38 PASS and one opt-in PostgreSQL skip, with no estate or model calls. The two actual API payload shapes and undeclared naive timestamp refusal are permanent regressions.
