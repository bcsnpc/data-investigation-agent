# Proposed transformation-code bindings — design only

2026-10-03. No inference producer or new execution capability is implemented.

## Scope and disagreement

Collect ordinary retained transformation definitions and propose exact scoped
bindings tagged INFERRED_FROM_CODE. Compiling both quantities and observing one
unfiltered aggregate agreement is a useful falsification test, not proof of
semantic equivalence. Different memberships can have equal sums; joins, nulls,
duplicates and compensating errors can also hide differences. “Trust” therefore
means eligible for a qualified exploratory comparison under a demonstrated
contract, never promotion to DECLARED_BY_DEFINITION or a verified cause.

## Collection

The adapter retrieves M partition expressions from the independently collected
semantic-model definition, SQL view definitions and their catalog dependencies
inside the approved database/schema, and collected notebook source plus ordinary
connection references. Each source unit retains its immutable content hash,
asset identity, definition receipt, context revision and coverage. Permission-
denied, truncated, unsupported or missing source cannot supply a complete binding.
Credentials and notebook secret literals are redacted before provider dispatch;
redaction affecting a source locator makes that locator unresolved. Discovery
never follows arbitrary endpoints embedded in code.

SQL views are currently excluded from governed execution. Collecting their text
does not silently make them executable: dependency/permission validation and an
appropriate adapter grammar must be separately delivered first. Dynamic notebook
execution and arbitrary M evaluation are outside scope.

## Closed proposal

A model translates one retained code unit, not an entire estate. The consumer
owns the proposal schema. A proposal contains only: context revision; code-unit
receipt and hash; exact source and destination asset IDs selected from supplied
approved candidates; exact column-ID mappings; retained source spans supporting
each mapping; and a closed description of supported operations and restrictions.
Provenance is the constant INFERRED_FROM_CODE. The alternative is UNRESOLVABLE
with a closed reason and source spans. No endpoint, credential, executable SQL,
expected total, arbitrary capability, confidence-based admission or free-form
mapping rule can be proposed. Native forms stay in the adapter; normalized
operation enums and support bounds come from the engine consumer.

## Verification and refusal

Validate the original code spans, hashes, approved asset membership and exact
connection scope. Compile both quantities through existing parser-governed
builders under explicit whole-entity context. Require an explicit faithful
contract for column mapping, grain, key multiplicity, joins, filters, dedupe,
nulls and update/delete handling; lack of one remains NOT_COMPARABLE. No name
search or inferred empty filter can repair missing declarations.

Perform the two independently attested, unfiltered aggregate reads. Unequal
values reject the proposed quantity equivalence. Equal values retain only
observed aggregate agreement, with snapshot grading and missing attestation
fields intact. Where keys/operations require membership checks, they are bounded
additional tests, not assumptions supplied by aggregate agreement. An approved
inferred binding remains a hypothesis and cannot explain a divergence as a
verified transformation merely because an earlier aggregate matched.

Absent source, unresolved scope, unsupported operation, ambiguous mapping,
incomparable quantity, failed read, unmatched attestation or budget exhaustion
produces a named refusal preserving its evidence. No retry or fallback identity.

## Provenance in outputs

Technical output names INFERRED_FROM_CODE, code receipt/spans, tested quantity
contract, observed agreement and omitted verification. Business output states
that the connection was inferred from processing instructions rather than
explicitly declared, and that agreeing totals do not prove the same entries or
data state were read. Both keep the actual ticket-answer relationship and action.
The renderer owns these limitations; model mechanism prose cannot duplicate them.

## Cost and limits

Per binding: zero new metadata requests if complete definitions are retained;
otherwise one bounded definition/catalog request per required source unit,
counting pagination and physical child requests individually. One proposal model
call. At least two diagnostic reads for the aggregate test, plus existing session
and permission overhead on each new object/connection. On current SQL routes
each first quantity costs four physical requests (one diagnostic, three guards);
two such routes cost eight physical requests before metadata and further key
tests. Guard reuse is recorded only where the existing guard contract permits it.
Provider tokens are bounded/reserved under the existing governed profile; no
settings increase is proposed here. Additional membership tests require their
own predeclared budget. No unbounded source-code sweep or automatic live profiling.

This cannot establish business intent, a global causal explanation, dynamic
runtime branch selection, cross-system transactionality, served-snapshot identity
or general equivalence from a sample. Unsupported code remains an estate gap.
Fixtures and independently authored expectations must be separate from runtime
context. Every attempted binding, failure and later investigation remains recorded.
