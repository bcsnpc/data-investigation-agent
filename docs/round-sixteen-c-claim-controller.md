# Round Sixteen C: confirmed-claim execution

The new controller executes a retained user-confirmed claim once. Its request contains only the claim ID, revision and idempotency key. It cannot supply a query, another scope, keys, a field or a route. A transaction checks the current claim before acquiring its lease; repeating the same request returns the retained result, and a different request cannot start a second run.

The controller re-resolves the same target against the current retained catalog. Same identities and unchanged displayed interpretation may continue, with both catalog pins retained in the execution record. A missing target or changed interpretation holds for confirmation. Original claims and approval pins are unchanged.

`AdaptiveRuntime.begin_claim_process` creates an ordinary admitted process session and starts it without a planner. Every projection/page read uses `process_adapter`, the existing physical-request governor and diagnostic accounting. The run ceiling is at most the existing 12; configured lower ceilings remain binding. Claim adapters have no implicit model judgment provider. `finalize_claim_process` retains deterministic results and the actual receipts/counters, without synthesis or causal promotion.

Record projections require exact explicitly supplied integral keys and current field/dimension identities. Submitted key lists are normalized without guessing numbers from prose. Each projection has an independently recompiled native request contract; its hash and address must match the sealed receipt before reduction. The consumer renders each key's independent first observed change, global row/distinct-key/null counts, unique field values, or dimension groups. Duplicate keys cannot supply one field value. Missing reads are not absent records. Roles come from estate declarations; otherwise they remain undeclared.

Both outputs retain the confirmed request, a conservative completion/partial/unresolved ending, actual checked facts, and timing/attestation/coverage limits. Business text uses visible labels and ordinary words. Technical text retains receipt references and `SNAPSHOT_UNVERIFIED`. Different values alone cannot become a data-defect or business-correctness claim. Exact safe exception details use the existing failure-retention consumer in a private local table; public output receives its reference, not exception locals or secrets. Read receipts survive downstream failures; model authorisation/billing/dollar stops are persisted and propagated.

Unsupported scope is explicit: screenshot context without a compiled filter/security scope, textual time/filter scope for Copy projections, visual restrictions not translated into equivalent record projections, and cross-model projection scope hold before data. Existing legacy quantity/definition APIs remain unchanged; new claim execution refuses where a faithful legacy admission is absent. Definition and filter questions do not silently become page-value comparisons. The installed projection compiler supports the declared semantic/landing/application Copy chain, not arbitrary transformations; causal step inspection and general date/string decomposition are not implemented here.
