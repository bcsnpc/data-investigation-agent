# Round Sixteen B ? claim intake controller

Claim intake is additive: existing visual-form and ticket APIs retain their contract. `/api/workspace/claims` accepts user text, submitted claim facts and an optional retained screenshot review. It records observed and expected figures separately, the metric in the user's words, direction, comparator, records/visuals/page/report scope, time, filters, examples and guessed cause. A suggested cause never decides the outcome.

Facts retain exact input spans, form pointers or trusted screenshot review positions and hashes. Explicit Report/Page/Visual lines and supported Power BI links are preserved before model judgment. Generic governed extraction returns token references and consumer enums; code extracts the exact text and validates figure precision. One rejected extraction gets one retry; a second rejection is a durable HELD claim. Authentication/billing failures propagate rather than becoming an intake finding. The provider uses the existing daily and dollar guards with a 32,000-character maximum, irrespective of agent-mode overrides.

Questions distinguish a supplied name from an unresolved definition binding. A consumer validator rejects requests for settled facts. Record complaints may request one example; page freshness needs no single numeric figure. Candidate mappings are derived from actual scoped catalog definitions and glossary evidence. Specific glossary targets cannot expand or cross a report boundary. Ambiguous visual scope asks which visible objects are included. Explicit multiple metrics/cards remain a MULTIPLE envelope, never an implicit single-target choice.

The user sees an interpretation naming the actual report/page/visuals and the settled comparison, time, filters and examples, in plain words. No raw JSON or internal IDs are displayed. Confirmation is explicit and records the exact accepted request, displayed interpretation hash and local-operator provenance. It creates `PLAN_ONLY`, with `executed: false`; Part C owns dispatch. A catalog change re-resolves stable objects. Missing/changed targets ask one current-target question; changed interpretation wording requires fresh confirmation. User corrections preserve old facts as superseded.

Exact tapes use recorder version v13 with claim submit/reply/confirm and screenshot identify/confirm operations. Version v12 remains supported unchanged. The replay dispatcher invokes the same controller. Projected interactive claim/screenshot intake refuses before raw persistence because image/context projection is not yet covered; there is no exact/raw fallback.

Focused validation: 35 controller/provider/glossary integration checks passed, followed by 26 controller/provider/tape checks with overlap. The synthetic claim submit and confirmation replay byte-identically with sockets and providers denied. Old clean-engine tape integration checks will run after the root freezes source; dirty-source capture was correctly refused, not bypassed. [The historical question audit](round-sixteen-b-question-policy-audit.md) is explicitly policy-only, not current extractor accuracy.

No estate reads, model requests, identity changes, old tape edits or acceptance expectation changes were made by this implementation subtask.
