# Round Sixteen B4 - estate glossary

The glossary is an estate-scoped, many-to-many graph in the existing installation catalog. Its append-only, hash-linked events carry a schema version and revision. Mutations require the expected revision; concurrent editors cannot overwrite one another. A glossary link connects typed phrase, concept, report-label, model-measure, model-column or declared-source-column nodes and records the retained evidence explaining that relationship.

Definition seeding uses exact current measure names and visual labels, together with the visual's actual measure references. It does not create semantic synonyms. A model-inferred link remains INFERRED until a separately retained user clarification or steward entry confirms that exact link. The original inference remains in history. Confirmed links are available to claim intake without another naming question; inferred links are returned as confirmation candidates. Multiple surviving meanings remain multiple candidates.

The server evidence lookup supplies the original retained record, its hash, actor and the relationship it supports. A caller-supplied `confirmed=true`, a model actor, an unrelated receipt or an invented catalog ID cannot establish authority. The catalog namespace is reserved for the definition seeder. Unknown references are refused on creation. Changed model contexts, revisions, definitions or supporting evidence prevent old links from resolving, even if display names remain unchanged.

The module is `investigator.claim_glossary.EstateGlossary(database, estate_id, evidence_lookup=...)`. `resolve(phrase, catalog)` returns catalog-backed model/measure identities, optional report/page/visual scope, readable labels, evidence IDs and CONFIRMED or INFERRED status. The private IDs identify objects in structured state; they are not substituted for visible names. The ClaimIntake controller owns intersection with the ticket's settled scope and the final interpretation confirmation.

Accepted claim interpretations are learned only after the controller commits the exact accepted request. `RetainedClaimEvidence` reloads that persisted claim and verifies its body hash, revision, current catalog, original settled facts, displayed interpretation, acceptance document and history. It supplies the local operator session as the actor; it does not invent a named human identity. Only a single phrase paired with a single selected measure is learned automatically. Multi-metric claims need individual link confirmation, and stale inferred links remain in history instead of being promoted under a changed context. Workspace integration proves that the accepted claim creates a reusable confirmed link through the actual lazy callback.

Source-column links require explicit source-column entries from retained metadata in the supplied catalog. The ordinary compact intake catalog does not expose that registry today; no source column is guessed from a familiar name. The graph can retain such links when an installation supplies the declared registry, but this implementation does not claim that the live fixture already has those links.

Privacy uses the existing installation-aware SQLite connection. Projected installations keep raw pages in memory and write projected images through their established persistence boundary. Persisted phrases retain their exact bytes; normalisation happens only during lookup, avoiding a new spelling that could escape value projection. The synthetic test writes and cold-loads a projected glossary and checks that neither the raw sensitive value nor a case-folded copy exists on disk.

Validation: the combined glossary, retained-confirmation, Workspace integration and ClaimIntake suite passes 45 tests. A combined glossary, privacy-storage and existing intake-confirmation run passed 43 tests before the subsequent context-pin regression was added. Tests cover ambiguous graph paths, cycles, explicit confirmation, malicious self-confirmation, unrelated evidence, stale definitions/context/evidence, isolated estates, optimistic revision conflicts, tampered history, visible labels, declared source columns and projected storage. No estate or model calls were used. One initial combined command named a nonexistent `test_claim_facts` module and failed import; the corrected explicit suite passes. The integrated glossary, controller, provider, Workspace HTTP and screenshot suite subsequently passed 65 tests. The original integration tests exposed a real scope leak: a visual-specific glossary link expanded to other same-measure visuals, including another report. The controller now intersects that link with its original visual/report scope; both regressions pass.

## DECIDED WITHOUT REVIEW

- Use the existing privacy-aware installation catalog instead of a separate JSON file. This keeps privacy projection, installation isolation and transaction rules on the same storage boundary.
- Preserve exact phrase bytes and compare their normalised forms transiently. Persisting normalised sensitive text was rejected because exact-value projection would not necessarily recognise it.
- Pin compact catalog entries to their model context and revision as well as their contents. Compact measure entries omit DAX expressions, so name/ID equality alone cannot preserve old authority.
- Require evidence lookup from retained server records for non-definition links. A model-provided provenance string is not evidence that a relationship was confirmed.

- Learn one phrase-to-measure relationship from the actual accepted interpretation, rather than treating a model candidate marked CONFIRMED as user approval. Keep multi-metric links unlearned until their individual relationships are established.
